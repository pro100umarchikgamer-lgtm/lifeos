## Intended experience

- Control opens actual user results, supports bounded name/email/ID search and pagination, and presents actions from user cards, support threads and recovery cases. Names are voluntary account metadata, never mined from family profiles or private records. Missing names remain visibly unspecified.
- Recovery can start from an external-email/manual contact or a ticket from a different account. The operator explicitly selects the original target. A ticket author never proves ownership of that target. Password-reset mail goes only to the stored verified target address; account MFA stays enabled. Original authenticated owners privately confirm cases/choose deleted records and redeem existing owner-only restoration grants. Staff initiates, guides and approves, without reading private bodies or impersonation.
- Staff roles have readable descriptions and a capability matrix. Owner/admin may restrict eligible lower-ranked staff to a subset of role capabilities, including at invitation time. Deny wins across roles. Effective capabilities are checked on every server request and again when an old invitation is redeemed. Existing hierarchy, revision, last-owner and MFA rules remain.
- Existing all/users announcements retain publication-snapshot semantics. A separate newcomers audience automatically reaches future verified accounts on their first eligible signed-in app open. It requires no UUIDs. Publication establishes an exact cohort boundary (including same-second registration); an account receives at most one newcomer welcome, and presented/dismissed state survives reloads/devices. Scheduling, cancellation and explicit indefinite duration are supported for this mode; previous audience limits remain unchanged. UI says after registration rather than promising guest/offline delivery.
- Every meaningful field/button has plain-language purpose/outcome help. Advanced targeting/percentage/reason controls disclose progressively. Existing UI flags either gain a real, tested consumer or are removed from active controls; no decorative product switches. No security/billing bypass settings.
- A shared install action appears at existing installation/help/profile/onboarding placements. Supported Chrome prompts use a real user gesture and event; cancellation/retry/installed states are honest. iPad/iPhone Chrome uses concise Share → Add to Home Screen → Add guidance because JavaScript cannot invoke that OS action. No automatic permission/dialog spam or auth tokens in URLs.
- New video requirements are tracked in `delivery/control-feedback-nov16/video-review/VIDEO_REVIEW.md`: anchored field dropdowns, actionable Native balance, richer Native Today, correct personal labels/management content, saved Web section on refresh, theme-matched initial splash and clearly visible saturation changes. ## Architecture and interfaces

Extend existing Python modules with small helpers and additive migration024+; do not change positional users/staff inserts. New metadata tables must participate in account erasure, import compatibility, tests and backups. Do not send production messages, broadcasts or change live staff restrictions merely to test.

Directory: GET `/control/api/users?search=&before=&limit=` returns existing `users` plus `next_before`; each safe user projection adds optional `display_name`, name source and safe status/activity metadata. Canonical optional account identity is self-managed through GET/POST `/account/api/identity` and `/v1/account/identity`; no automatic family-name extraction. User card keeps current entitlements/devices and adds recovery entry.

Rights: GET `/control/api/permissions` returns assignable role/capability keys and ranks; GET staff and session expose base/effective/denied lists. Existing staff/update and staff/invite accept optional `denied_permissions`; omission preserves existing restrictions. Role baseline minus denies is the maximum authority; assignment cannot delegate permissions the issuer lacks. Owner cannot be modified or newly invited.

Cases: GET/POST `/control/api/recovery-cases`, GET `/control/api/recovery-case?id=`, POST `/control/api/recovery-cases/update`. Create body: target_user_id, optional ticket_id, kind access/records, reason. Updates: id, revision, action send_reset/close/cancel, reason. Detail contains safe target identity, source, state and target-filtered existing requests, not record payloads. GET own `/account/api/recovery-cases`, GET `/account/api/recovery-case?id=`, POST `/account/api/recovery-cases/confirm` are target-authenticated; expose matching bearer aliases where needed. Case confirmation is separate from per-record owner consent. Existing requests/approve/prepare/commit remain authoritative.

Announcements: logical API `audience=newcomers`, manual IDs empty, `no_expiry` supported. Store targeting separately to preserve old audience CHECK/semantics; lazy recipient attachment and per-account welcome claim run transactionally. Persist exact boundary exclusions for registration ties; do not store a whole global user snapshot for future targeting. Preserve read/presented/dismiss, retention, erasure and cancellation.

Frontend: implement a cohesive Control workbench module reusing existing DOM/API/style helpers; web.js contains small integration wrappers. New public static assets need explicit server allowlists, CSP/SW/release registration. PWA worker owns install module/HTML/app hooks; backend worker owns backend/web.py, so send PWA server edits as a bounded integration request. Root owns shared localization integration and remaining Web feedback.
